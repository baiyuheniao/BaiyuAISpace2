# 自主维护交接日志

## 2026-08-22：Agent 强制收尾失败不再静默复位

### 变更

- 工具轮耗尽后的无工具强制收尾现在必须产出非空文字；请求错误、空文字和异常工具调用
  都会作为真实错误上报。
- 已完成工具调用的摘要仍会先写入 scratchpad，随后才把错误交给 Agent 外层循环处理。
- 增加纯单元测试，覆盖正常文字、空文字、异常工具调用和请求错误四类结果。

### 根因与用户影响

旧实现对强制收尾的失败分支只写后端警告，随后仍返回 `Ok(())` 并把 Agent 复位成
`Idle`。用户会看到 Agent 结束运行却没有任何回复，工作区也没有可见错误或主 Agent 通知，
难以区分模型空响应、网络故障和正常完成。

现在这类情况进入既有故障处理：写入可见错误日志、将 Agent 标为 `Error`，并按原规则通知
主 Agent；已完成的工具摘要不会因为报错而丢失。

### 验证

- 新测试不访问网络或真实模型，只验证强制收尾结果分类。
- `git diff --check` 通过；Windows / Ubuntu 的前端构建、Rust 编译和单元测试由 PR CI 验证。

### 风险与回滚

- 只改变此前被误判为成功的三类失败结果；正常非空回复路径不变。
- 不修改请求参数、重试/超时配置、数据库结构或前端协议。
- 强制收尾失败后 Agent 会明确进入 `Error`，这是已有错误恢复和主 Agent 通知流程。

### 下一步

- 继续检查 Agent 从暂时性模型错误恢复时的交互入口，并在真实 Windows WebView2 环境验证
  错误提示与重试体验。

## 2026-08-21：Agent 非流式请求的 600 秒改为整轮总预算

### 变更

- 为 `run_turn` 的完整网络流程增加外层总时长预算，覆盖首次请求、重试间隔、所有重试
  以及成功响应的 body 读取。
- 保留现有的快速连接失败、429 / 5xx / 529 过载重试；不改变配置值和请求体。
- 新增 250ms 确定性测试，证明即使单次超时 100ms、允许 10 次重试，整轮仍会在总预算
  到点后停止，而不会把预算按尝试次数重复计算。

### 根因与用户影响

`reqwest::Client::timeout(600s)` 是每次请求各自的超时，`send_with_retry` 默认还允许 3 次
重试。极端无响应场景可能连续等待 4 个 600 秒，总计约 40 分钟，与代码注释和 Issue #86
所称的“600 秒总超时”不一致。Agent 会长时间保持 Running，用户也难以判断是否卡死。

人话解释：以前每次重拨电话都会重新发一张 10 分钟倒计时券，最多可能等 40 分钟；现在
整轮只有一张 10 分钟券，快速失败仍可重拨，但总等待不会越滚越长。

### 验证

- 新测试只使用回环地址，不访问外网或真实模型。
- 既有“严格按配置重试”和“取消可立即中断”测试继续保留。
- `git diff --check` 通过；Windows / Ubuntu 完整构建与单元测试由 PR CI 验证。

### 风险与回滚

- 600 秒数值不变，只把它从“每次尝试”纠正为“完整往返”。
- 在接近 600 秒才失败的请求上，不会再继续重试；这是避免 40 分钟悬挂和重复模型工作的
  有意保护。快速失败仍会在总预算内按原策略重试。
- 新错误沿用现有字符串序列化，不改前后端协议结构。

### 下一步

- CI 和真实 Windows 环境继续观察总超时提示是否清晰。
- Issue #86 的“超时不会重试”和“600 秒实际会固定结束”均已有自动测试；剩余是否要按
  provider 调整 600 秒数值，应等真实慢模型数据再决定。

## 2026-08-19：非流式超时重试的确定性回归测试

### 变更

- 为 `send_with_retry` 增加本地 TCP 超时测试：模拟服务端接受连接但始终不返回响应。
- 测试使用 100ms 客户端超时和 `retry_count=2`，要求最终返回真实的 reqwest 超时，
  并且服务端恰好观察到 3 次连接（首次请求 + 2 次重试）。

### 根因与用户影响

Issue #86 记录时认为 Agent Team 的非流式超时不在重试范围内，但当前实现已经把连接和
超时错误纳入 `send_with_retry`。此前没有自动测试锁定这一事实，后续重构可能让超时静默
退出重试范围，或出现多试/少试造成额外等待与费用。

人话解释：现在自动测试会用一个“接电话但始终不说话”的假模型，确认软件等待超时后只按
设定次数重拨，次数不能多也不能少，最后还要明确告诉上层这是超时。

### 验证

- 测试完全使用回环地址，不依赖外网、真实模型或等待 600 秒。
- `git diff --check` 通过；Windows / Ubuntu 的完整构建与单元测试由 PR CI 验证。

### 风险与回滚

- 仅增加测试和交接记录，不修改运行时请求、超时值、重试值或数据库。
- 测试总门禁为 2 秒，失败会快速退出，不会拖慢 CI 数分钟。

### 下一步

- Issue #86 中“超时完全不会重试”的描述已过时，但 600 秒固定上限是否适合所有模型仍
  缺少真实数据；继续保持不调整数值。
- 下一步聚焦超时重试全部耗尽后 Agent 的状态与用户重试入口。

## 2026-08-18：取消后的 Agent 循环不再误报错误

### 变更

- `run_agent_loop` 收到模型请求错误后，先检查所属取消令牌；若 Agent / 工作组正在
  正常停止，直接结束循环。
- 停止期间不再写 `error` 工作区日志、不再尝试把已删除 Agent 回写为 `Error`，也不会
  向主 Agent 发送误报或触发错误终态验收。

### 根因与用户影响

上一项修复让停止信号能够中断模型 HTTP 请求，但中断会沿用现有“请求已取消”错误返回。
后台循环旧的统一错误分支无法区分“生命周期正常停止”和真实故障，因此仍会执行一遍故障
收尾。删除工作组时可能留下误导日志，并对已经删除的记录做无意义状态写入。

人话解释：电话已经按要求挂断了，旧流程却还会补写一张“通话故障单”；现在正常挂断会
安静收尾，真正的请求错误仍按原流程上报。

### 验证

- 静态核对取消分支位于任何错误日志、数据库状态写入和主 Agent 通知之前。
- `git diff --check` 通过；Windows / Ubuntu 的完整构建和单元测试由 PR CI 验证。

### 风险与回滚

- 只有取消令牌已经触发时跳过错误处理；未取消的超时、鉴权、服务商错误仍进入原分支。
- 不修改数据库结构、网络参数或前端协议。

### 下一步

- 继续为 Issue #86 的真实超时耗尽场景设计可控状态机测试，重点确认暂时性网络故障后的
  Agent 恢复体验。

## 2026-08-18：Agent Team 停止信号可中断模型请求

### 变更

- `send_with_retry` 在 HTTP 请求正在等待响应时也监听 `CancellationToken`；此前只在
  两次重试之间的等待期监听。
- Agent Team 的普通推理、轮数求救和强制收尾三条 `run_turn` 路径全部传入所属
  Agent 的停止令牌；普通聊天和上下文压缩继续使用原有不可取消入口，行为不变。
- 增加本地 TCP 确定性测试：服务端接受连接但不返回响应，取消令牌触发后请求必须
  在 2 秒门禁内结束，而不是等到 HTTP 总超时。

### 根因与用户影响

删除 Agent 或工作组时，后台循环会收到停止信号，但旧实现一旦已经进入非流式 HTTP
请求，就只能继续等待最多 600 秒，并可能按默认策略继续重试。数据库对象虽然已经删除，
后台网络任务仍可能长期占用资源，结束后还会走一遍错误收尾路径。

人话解释：原来“停止 Agent”只能阻止它开始下一步，阻止不了已经拨出去、一直没人接的
电话；现在停止信号会立刻挂断这通电话。

### 验证

- 新增 Tokio 本地 HTTP 取消测试，不依赖真实模型或外网。
- `git diff --check` 通过；完整的前端构建、Rust 编译和单元测试由 PR 的 Windows / Ubuntu
  CI 矩阵执行后再决定是否合并。

### 风险与回滚

- 不修改 600 秒总超时、重试次数、模型请求体或数据库。
- 仅 Agent/工作组真正被取消时提前结束请求；正常请求路径不受影响。
- 错误仍复用现有“请求已取消”类型，不新增前后端协议字段。

### 下一步

- Issue #86 的固定超时值仍需真实慢模型数据支撑；当前不拍脑袋调整上限。
- 后续可为“超时重试耗尽后 Agent 的恢复状态”补充状态机测试，避免短暂网络故障让
  Agent 长时间停在 Error。

## 2026-08-17：Agent Team 全局事件监听竞态

### 变更

- 为 `src/stores/workspace.ts` 的 `initListeners()` 增加初始化中的 Promise 互斥。
- 并发调用现在复用同一轮监听器注册，不会分别注册两套全局监听器。
- 注册过程失败时主动注销已经成功注册的部分监听器，保留后续重试能力。
- 消息、活动日志及五类待处理事项增加按事件 ID 去重，防止重复事件污染界面状态。

### 根因与用户影响

`Layout.vue` 和 `AgentTeamView.vue` 都会在挂载时调用 `initListeners()`。旧代码只通过
`unlistenFns.length` 判断是否已经初始化，而该数组要等所有异步 `listen()` 完成后才会赋值。
两处调用重叠时都会看到长度为 0，从而注册两整套监听器。用户可能看到同一条 Agent 消息、
日志或审批卡片出现两次；重复审批还会触发“事项不存在或已处理”的二次错误。

人话解释：应用启动 Agent Team 页面时，原来可能把同一个“消息接收器”装两遍，因此一条消息
会被界面接收两次。现在同一时刻只允许安装一次，并且相同编号的事件只展示一次。

### 验证

- 静态路径核对：`Layout.vue` 与 `AgentTeamView.vue` 的并发入口均会命中同一个初始化 Promise。
- 重复事件核对：消息、日志使用后端事件 `id` 去重；提议、休眠、轮数、提问、工具审批分别使用自身 ID 去重。
- 本地完整构建暂不可执行：当前运行环境缺少 Rust 工具链，且前端依赖镜像无法从受限网络下载。
- 提交后由仓库现有 GitHub Actions 执行前端构建与 Rust 编译门禁；在门禁通过前不合并或发布。

### 风险与回滚

- 变更只影响前端事件订阅与内存队列，不修改 SQLite、Agent 推理或工具执行逻辑。
- 若出现监听初始化异常，可回滚本次提交；失败分支会清理部分注册，避免残留半套监听器。

### 下一步

- GitHub Actions 通过后，在 Windows 真实应用中快速切入 Agent Team，确认单条消息、日志与审批卡片均只出现一次。
- 继续复现 Issue #86 的 600 秒非流式请求超时；在取得真实超时证据前不拍脑袋修改上限。
